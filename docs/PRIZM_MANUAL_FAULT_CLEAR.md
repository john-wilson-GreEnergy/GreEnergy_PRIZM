# PRIZM_MANUAL_FAULT_CLEAR

## Overview
This document describes the manual fault clear capability for local EMS Turtle systems running the PRIZM stack. The capability enables an authorized technician to safely issue a raw binary protobuf \`ManualClearDeviceFault\` command targeting a specific piece of equipment with an active fault, provided the local EMS node actively flags it as eligible.

## Architecture

*   **Source Endpoint**: GET \`/tools/monitor/ems/blockviewer/data\`
    *   This provides the active real-time blockviewer topology structure, detailing every active sub-module (BESS controllers, arrays, strings).
    *   The `allowFaultReset` boolean attribute drives eligibility. If this flag is `true`, the local node will accept a command targeting the `entityKeyToken`.
*   **Command Endpoint**: POST \`/tools/controls/ems/command\`
    *   Expects raw protobuf binary bytes `application/octet-stream`.

## Protobuf Command Shape

\`\`\`protobuf
syntax = "proto3";

package turtle.controls;

message CommandTarget {
    string endpointType = 1;
}

message CommandSource {
    string endpointType = 1;
}

message ManualClearDeviceFault {
    string entityKey = 1;
}

message CommandPayload {
    ManualClearDeviceFault manualClearDeviceFault = 100; 
}

message Command {
    string commandId = 1;
    CommandTarget commandTarget = 2;
    CommandSource commandSource = 3;
    CommandPayload commandPayload = 4;
    string username = 5;
}
\`\`\`

The payload sent ensures:
*   `commandSource.endpointType = GOBLIN`
*   `commandTarget.endpointType = BLOCK`

## Safety Gating
1.  **Blockviewer Scan**: The UI displays only components explicitly permitted by the EMS node via `allowFaultReset=true`.
2.  **Pre-Flight Verification**: Executing the command triggers a hard secondary fetch of the blockviewer endpoint from the backend immediately before byte generation. If `allowFaultReset` has flipped to `false` or the entity is missing, the request is aborted.
3.  **Communication Required**: The component must be reporting `communicating=true`.
4.  **Admin Override Disabled**: Currently no override bypasses the `allowFaultReset` flag.
5.  **Audit Logs**: All events are logged.

## Result Processing
An HTTP 200 from the target POST endpoint **only means the command has been queued** on the local node. 
A synchronous response will rarely map directly to a successful fault clear. A post-command `blockviewer` scan is executed to determine if the `statusMessage` cleared or the `allowFaultReset` eligibility flipped back to `false`.

## Operational Requirements
*   A target profile must have an active EMS LAN connection.
*   Token string MUST match the exact signature generated by the topology.
*   A user execution confirmation string (`CLEAR FAULT` or token) is mandated.

## Known Dry-Run Validation Results
*   Minimal payload returned `INVALID_COMMAND_TARGET / HTTP 501`
*   Full envelope `GOBLIN → BLOCK` returned `QUEUED / HTTP 200`
*   Live execution requires `allowFaultReset=true` from current EMS topology
