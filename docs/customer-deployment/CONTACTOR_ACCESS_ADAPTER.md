Before execution, reserve the exact command and target in a private, versioned receipt ledger. The reservation is persisted with file and parent-directory synchronization before calling the equipment service. The runtime never recreates a missing ledger. Independent processes serialize ledger mutations with an exclusive lock; a crash-held lock fails closed and requires supervised host-side recovery, never automatic lock stealing.

Reservations and unverified outcomes block that target across accounts, browser reloads and process restarts. Verified outcomes permit a new explicitly confirmed command with a new ID. Recorded IDs are never automatically aged out or replayed. Missing, malformed, insecure, oversized, locked or full storage prevents dispatch. A failed final save leaves the original reservation unresolved. This is at-most-once attempt protection while the ledger is preserved, not exactly-once device delivery, an EMS lock or a substitute for electrical interlocks. Administrator deletion/rollback of state cannot be made safe by this file ledger.

Read-only saved-receipt access requires the originating account, enrolled site and `history.view`; another account receives a generic unavailable response. Saved verification is historical evidence, never a fresh equipment-state claim. No automatic retry, reset, reconciliation, pruning or target release is added. A reviewed reconciliation tool, backup/restore procedure, retention policy and supervised live parity remain release gates.

Provision an empty ledger only for a new pilot with no in-flight commands, or after explicitly reconciling previous commands. Do not initialize a replacement after data loss. No real security directory will be created or changed during implementation; tests use private temporary directories and simulated dispatch.

## Signed-in review UI (next integration slice)

The session advertises single-string control availability only when the private adapter is enabled and the account has a matching-site control grant. This hint is not authorization. An explicit row action performs a read-only, server-authorized review request for that string. It returns an expiring topology revision; submission must match that reviewed revision. No automatic writes, typed confirmation phrase or safety override controls are introduced.

The review names site, array, string, action and selected reason. Open/close are explicit choices; the final button names the action and target. Stale telemetry, expired review and sign-out disable execution. While sending, double-clicks cannot submit again. Acceptance and physical verification remain distinct. An uncertain result never retries; the client blocks that target in the workspace and the durable server ledger keeps it blocked across reloads and restarts. Show the command ID for supervised reconciliation. Browser/session loss cannot cancel a command already sent. A saved-receipt viewer and supervised reconciliation workflow remain release gates.

Validation uses simulated control services only. Activation and any real account grants remain separate approved deployment steps.

Architecture: authenticated pilot route → strict single-string intent → enrolled cached topology and target grant → bounded execution adapter → existing EMS contactor service → existing read-only verification.

This increment is disabled unless private enrollment explicitly sets `allowSingleStringContactors: true`. Provisioning presets still grant no controls. Legacy aliases remain blocked in pilot mode. The pilot screen is read-only by default; it exposes target review only to accounts with matching-site contactor grants when the adapter is enabled. No live activation, account grant, equipment command, restart or deployment is part of this work.

The request supplies only a command ID, open/close, numeric array/string, confirmation, a reason and the reviewed topology revision. It cannot supply a destination, principal, safety override, array-wide selector or topology inventory. The server derives target IDs as `array:N:string:N` from a fresh, LIVE, enrolled canonical snapshot. Site and topology are pinned at admission, the reviewed revision must match, and session/grants/topology/freshness are checked again immediately before dispatch, after durable audit intent. Electrical protection overrides stay off.

The existing service receives trusted execution hooks separately from request JSON, preserves shared target locks, records the authenticated actor, and namespaces its short-term deduplication by server identity. An outer bounded in-memory registry coalesces current-session duplicates and retains IDs for 24 hours without evicting pending commands. Beneath it, the durable ledger retains command IDs without automatic expiry and blocks unresolved targets across accounts and restarts. Unknown outcomes are never automatically retried. Concurrent independent ledger mutations fail closed rather than queue; this conservative pilot favors avoiding duplicate writes over availability. Storage is capped at 512 records; reviewed archival/reconciliation is required before broader deployment.

Readback is not a write and does not resend a command. Revocation cannot undo an already dispatched command; it prevents new dispatch and result disclosure. HTTP acceptance is not proof of contactor movement. Responses expose acceptance and verification separately, with no raw controller response or destination URL.

Validation is offline with outbound networking blocked. Single-target permission, forged fields, stale/changed topology, revoked sessions, failed audit, duplicate IDs and sanitization must be covered. Production remains gated on reviewed TLS, audit retention, supervised restart reconciliation and live parity.
